# Native Herdr Tasks pane

A read-only native GPUI view of the same per-Pi-session JSON used by pi-tasks. No browser, second Pi process, task database, model call, HTTP server or task editing.

## Install and open

From an updated local Pi terminal already displayed in Herdr, run `/works herdr-on`, or enable `pi-tasks.herdrPanel.enabled` for automatic startup. The command validates the session file and source terminal, installs missing content assets into `<Herdr app home>/mods/pi-tasks/`, and opens beside that exact terminal, or stacks below its same-session Loops/Monitors pane if already open. Reopening focuses the existing Tasks pane. Automatic startup runs the same setup at each session start and replaces this terminal’s Tasks pane from an earlier session; it stays silent when Herdr is unavailable or setup fails, while the command reports the reason. The opener uses the normal desktop app home (`~/.config/herdr-app`, or the `XDG_CONFIG_HOME` equivalent), ignoring inherited `HERDR_APP_HOME` fixture overrides for both app commands and asset installation. Existing/customized mod files are never overwritten by the command; upgrade those assets explicitly after keeping a backup.

The always-visible × belongs to Herdr's real pane header, not the content view. On first setup the command uses Herdr's official clone operations to create:

- a personal `mods/pi-tasks-pane-header/`, copying the current header and assets; its original renderer is kept as `base.js`;
- a personal `layouts/pi-tasks-<current-layout>.json`, selected for this window, with the Tasks-aware header.

Original layout/header files remain untouched. Non-Tasks headers use the copied original renderer and behavior. A header shorter than 32px is raised to 32px in the personal layout for the close target. Switch back to the original layout to undo the layout selection. The current layout must already have an always-visible top pane-header mod; absent/bottom/hover-only or mixed headers report a bounded setup error instead of changing unrelated structures. Existing conflicting personal assets are preserved, not replaced. A compatible existing personal Tasks layout may be reused.

After changing the installed extension, run `/reload`, or restart Pi and resume the same session if an old loaded module has no snapshot binding. Pane-header copies only pick up edited mod code when their pane is created, so closing and reopening the Tasks pane applies a refreshed header. `/works compact-off` hides only the compact Pi TUI; tracking and the native view continue. Reopening focuses the existing same-session view, never another writer. `/works herdr-off` closes only matching Tasks mod panes in this terminal’s tab; tracking and the compact display continue.

Developer checks:

```sh
herdr-app check ~/.config/herdr-app/mods/pi-tasks
herdr-app check ~/.config/herdr-app/mods/pi-tasks-pane-header
```

`header.js` in this bundle is an installation template. Its `./base.js` is supplied by cloning the actual configured header, not bundled as an unrelated copy of Herdr's code. Never edit Herdr's shipped `pane` mod in place.

## Behavior

- Compact real Work → Task rows, newest Work first with older Works below; task order within each Work stays unchanged. No invented subtasks. Activate a Work name to fold its tasks, or a task name to toggle an unboxed inline Final thoughts. A blocked task shows its authoritative blocked reason and any stored `Dependent on: User decision` or `Dependent on: Another agent` beside the Final thoughts label; a legacy blocked record without a dependency shows no invented label, and a task without a thought shows an honest empty label. Stored `taskInfo` metadata (owner line, links, paths, parent IDs) is never rendered. Work and task title buttons use the same underline focus affordance, so clicking one does not paint a selection-like background. The selected task is highlighted across its whole row. Double-clicking counts as one activation instead of immediately toggling the thought twice.
- Leading loader only while the task is genuinely running, `!` for blocked, `✓` for complete, quiet idle/cancelled marks. No session/connection bar, top counts, extra owner/status fact line or Read-only footer.
- Plain right-aligned progress and measured effort. Work completion averages noncancelled tasks; unknown propagates. Effort includes cancelled time and imported cumulative reports once. Unknown is `—`, known zero `0s`.
- A measured clock ticks only for a live source actually working on the selected measured task. Saved/offline/paused values freeze; time is not wall-clock age or ETA. Native spinner animation is independent of clock redraws. This Herdr API does not expose an OS reduced-motion preference.
- `Agent ↗` appears next to a task with a valid existing live delegate link. Activation rechecks that exact link: a terminal that owns a pane gets normal app focus, while a pane-less Core child opens its own `terminal.peek` overlay over the current tab; a deeper child is recognized by its nonempty Core parent record. It never navigates to the parent, launches an agent, or reports a silent success. Work rows have no Agent button. Agent and task-thought controls are independent.
- No three-dot trigger or native action menu is shown. Copy and repository actions remain available through the `/works` dashboard and commands; reopen the native pane to refresh after a watcher error.
- The native header × targets only the exact verified terminal-null pi-tasks pane. Closing leaves Pi, agents and tracking intact. It remains present for populated, empty, loading and error content.
- Snapshot version/session identity and record structure are validated, including a blocked task's optional two-value dependency; the directory is watched for atomic replacement. Invalid/missing files show an error, not stale rows. No authoritative record cache or mod-local task persistence is added.
- The persistent pane header carries one compact status dropdown before its ×: **All statuses** (default), **Active**, **Blocked**, **Completed**, **Cancelled**. It filters tasks by their stored status, never works, and the stored status decides the match — a running task is Active. Filtered views keep only matching tasks and the Works that contain them, in the existing newest-Work-first and original task order; Work progress and effort stay totals for every task of the Work, and task status, estimates, timing and records are untouched. A selection with no match shows a status-specific empty state, and a changed selection starts at the top of the list. The selection is view state for that exact pane: it lives in Herdr's shared store under `pi-tasks-status:<paneId>` (the neighbouring Loops/Monitors header uses the same per-pane pattern) and is never written to a settings file or a task record.
- The menu is open state, not just a value: the header publishes it as `pi-tasks-status-open:<paneId>` so the view can close it. A press anywhere in the task list dismisses it, a press on the header row dismisses it, the trigger toggles it, an option selects and closes it, and Escape closes it; dismissing always keeps the selected status. Herdr's Select closes on presses inside its own mod, so the view supplies the press from its own root.
- A pane content copy receives only the props it was created with, so it cannot name its own pane. The opener therefore writes the hosting pane id to `<agentDir>/tasks/<sessionId>.pane` and passes its path as the `paneFile` prop; the view reads it beside the snapshot. A pane created before that hand-off carries no `paneFile` prop, and its stored props never change, so the view falls back to the live pane inventory: it finds the source terminal's tab and adopts the one Tasks pane there, which is the pane the opener split it into. An absent, missing, malformed or ambiguous answer leaves the view at **All statuses** instead of guessing another pane's selection. The dropdown anchors its menu to the trigger and grows downward, because a header at the top of a pane has no room above it.

Manual content props are `{sessionId, snapshot, terminal?, openCommand?, paneFile?}`. Bind the full Pi session ID and absolute task JSON path explicitly, never whichever terminal is focused. The source terminal's availability alone does not prove it still hosts that session. Only local file-backed sessions are supported.

`herdr-app check` proves loading and an initial render only. Populated native visual/interaction checks must separately verify file updates, inline Final thoughts, keyboard focus, linked Agent navigation (pane owner and pane-less child overlay), the status dropdown (menu placement, each status, no-match empty state, Work totals, two panes staying independent) and guarded close behavior. Browser mockups do not prove native behavior. The installed personal mod is not overwritten by package setup; refresh it explicitly to receive source changes.

Mod code and pane props have separate lifetimes. A pane's view is built from the mod files in `mods/` when the Herdr app starts or when the pane is created, so an edited mod reaches existing panes after an app restart or a closed-and-reopened pane. The props a pane was created with are stored in the Herdr core document and only a *new* pane from an extension that knows them can change them: a Pi process keeps the extension code it started with, so a pane it reopens still carries the older props until that Pi session is restarted or a new session opens the pane.
