# Implement

Use this skill as the coordination workflow for every tracked Work, including each subagent's local Work. Reuse it when already active rather than recursively invoking it. Specialized skills still own their behavior: research and review remain read-only; a resolved `grill-me` or `ui-ux-grill-me` interview authorizes implementation of the clarified scope without another permission prompt or `continue`; user-requested planning stays planning-only. Honor explicit interview-only or planning-only limits, leave unresolved material decisions and deferred scope unimplemented, and keep authorization, safety, and resource boundaries intact. Coordination never grants permission to edit, test, delegate, commit, or deploy beyond the owning skill and user request. Keep the process small, readable, and easy to resume.

Choose the smallest safe path to the authorized outcome. For small, isolated work, use one owner and one Todo per independently actionable outcome — not one per check or tool — keep the plan concise in the existing Work and Todo records, and create artifacts only when they help. Reach the verified outcome before adding speculative safeguards, delegates, DAGs, or reviews.

Keep one owner for coherent changes to the same shared mutable resource through implementation and verification. Define the resource and write boundary before dispatch. Parallel read-only work is allowed; do not mutate the resource concurrently without an explicit handoff. The handoff states what changed, the observation time, verification performed, and remaining work. Report findings outside the boundary to the owner. An independent reviewer may join at a stable milestone without turning implementation into several handoffs. Parallelize only when outcomes and mutable resources are independent, not merely separate files.

Before replying to the user, follow the global `talk-human` skill. Also follow `no-unit-tests` unless the user's latest request explicitly asks for unit tests. Follow the global `no-arbitrary-limits` skill for every implementation, fix, refactor, migration, and maintenance task: do not add unrequested capacity caps or ask about optional limits during implementation; explain relevant optional controls only after completion.

## Session coordination

Before executing requested work, including project investigation and project-file reads, call `WorkList` and `TodoList`, create or resume the relevant session-local Work, and create or update its Todos. Treat a distinct new actionable request as its own outcome and Todo even when it extends an existing Work. Never record it only by broadening workInfo, renaming an existing Todo, or blocking a previous Todo; reuse a Todo only when it genuinely owns the same outcome. Require a real `workId` and an active `taskId` for the current step; keep task status current with `TodoUpdate` and use `WorkUpdate` when shared scope or context changes. Reading the instructions and skills that govern the work, obtaining identity, and establishing tracking are the startup steps that come before execution, not a reason to invent IDs; the intentional First Mate coordinator shell restriction under Files is unchanged. If tracking tools or required IDs are unavailable, report the blocker and do not begin execution. Use `MonitorCreate` for long-running background commands; `AgentCreate` establishes the mandatory continuous Herdr worker subscription through pi-loop-monitor when available. Use `LoopCreate` only for a future or repeated wake. Keep in-flight work moving through concrete wakes — monitor or watcher signals, worker state changes, or a bounded `LoopCreate` with `maxFires` for a genuine recurring check. Never sleep-loop, poll indefinitely, or create an unbounded loop just to keep work alive. Plain conversation does not require a Work. Never create or update tracking, execute this workflow, or launch agents during `/ask` or `/btw`.

Works are collections of tasks with shared context, not executable records. Never assign a Work its own active, blocked, completed, or cancelled status, and do not pass status to Work tools. Tasks alone own status. Track each executable step as a Todo; continuation considers active tasks across all Works on the current session branch. Empty Works and blocked, completed, or cancelled tasks do not trigger continuation. Keep Work progress derived from task progress rather than adding a parent lifecycle. Group checks and tool runs under the outcome they serve instead of creating a Todo for each one, and skip a separate plan document when the Work and Todo records already carry the plan.

Before yielding or reporting a work item done, sweep every authorized outcome in the current Work. Pursue each one through documentation discovery, implementation, and verification; a failed step, partial worker result, or apparent blocker calls for diagnosis and recovery, not an early stop or another request for permission already granted. Each outcome must be verified completed, in flight with a named owner and a live continuation such as a monitor or watcher wake, or blocked on a precise user decision or another agent's output, with the required `dependentOn` classification and a reason that names the dependency and the check that will resume it. A generic external obstacle is not a blocked task status: continue safe work and report the unavailable dependency truthfully. An unowned "waiting" state or a "parent should decide" note is not a blocker. Do not silently narrow or defer a resolved scope into a different Todo: when an authorized interview resolves several branches, create one distinct tracked implementation outcome covering all resolved branches before splitting or narrowing scope, and dispatch it without asking again for permission the interview already granted. Honor explicit interview-only and planning-only limits, leave deferred decisions and other unauthorized work unimplemented, and keep continuing any other authorized outcome while one dependency is unresolved.

## Waiting without spinning

Choose the wait by what can actually wake the next useful step. Instructions and status labels are not wakes, and a task cannot be left active merely to keep a loop alive.

| Situation | Task state and wake | What not to do |
| --- | --- | --- |
| Waiting on a real delegated agent | Keep the parent task `blocked` with `dependentOn="another-agent"` and a reason naming the worker and the check that resumes it. Keep one continuous `hcTerminalId` monitor subscribed; its state-change signal is the wake. On a wake, inspect fresh output and artifacts. `done`, `idle`, process exit and notifications are inspection triggers, not completion proof. | Do not poll `AgentOutput`, `AgentStatus` or `MonitorList` on a timer, add one-shot waits, send repeated nudges, or mark work complete from status alone. |
| Waiting on a monitored process | Keep the task `active` with `owner: self`, record the process and expected result, create a command monitor with `onDone`, then yield. The monitor wake resumes that active task; process runtime alone is not a blocker. | Do not mark blocked for a build, test or other command, do not create an idle loop only to watch it, and do not poll output. |
| External service, tool failure or missing access | Keep the task active, preserve progress, continue other safe work, and report the concrete unavailable dependency and the exact action needed to resume. Such a failure is neither an agent output nor a user decision. | Do not invent `blocked`/`dependentOn`, retry unchanged work in a loop, or leave a vague waiting note with no owner or next action. If no safe action or wake remains, report the limit honestly instead of manufacturing one. |
| Stopped, empty or unchanged loop iteration | For a dynamic loop, call `LoopUpdate` once per wake with the real state; continue only when work remains, complete when the stop condition is met, and pause only for a genuine blocker. Fixed cron/event loops persist normally and need no update. An unchanged result is still a normal iteration. | Do not delete a healthy loop after a normal iteration, extend a dynamic loop only to stay alive, or write repeat filler to tasks or the user. |

Only a genuine user response, approval or permission uses `blocked` with `dependentOn="user-decision"`. Avoid repeated task updates that only restate waiting; significant state changes and the eventual verified outcome are the updates that matter.

## Rules

- Read repository instructions, then the relevant flow or architecture documentation once tracking is established, before making changes. Read every required source completely: when a file, log, delegated result or artifact exceeds one read, continue in bounded chunks until every needed part has been read, and never base a decision or a completion claim on a partial required source.
- When a task reaches an API key, token, password, or other secret value and the current user, repository, or task policy assigns custody to the user, use the global `secret-handoff` workflow for names-only identification and handoff. Do not infer that policy for unrelated projects.
- Resolve the system boundary early. Before designing or editing, determine from current source and explicit decisions whether the request continues the current system, starts fresh with new data, or migrates existing data or configuration. When that choice materially changes scope, risk or data and is not yet decided, surface it as a user decision before implementation; do not let a worker guess or revive an abandoned migration path. Record the decision in the Work/Todo context.
- Preserve unrelated changes and existing staged work.
- Follow the `Git authority` contract below; do not publish or deploy unless explicitly asked.
- Do not hard-code an answer for one example or bypass the owning boundary.
- Use resolved `grill-me` and `ui-ux-grill-me` decisions as requirements; deferred decisions are not requirements.
- For every task, choose `self` or `delegate` and record a short reason in the hidden `taskInfo` before execution, following the ownership decision below. A read-only review is not a substitute for considering implementation delegation.
- Keep `taskInfo` to hidden coordination metadata: the owner declaration, canonical artifact paths, parent IDs, links, and necessary constraints. Use concise `finalThoughts` for the only user-visible task text: `blockedReason` is the authoritative blocked dependency, a completed task states the verified result and limits, and an active task updates only when something significant changed. A newly blocked task also needs `dependentOn="user-decision"` or `dependentOn="another-agent"`; task details show the chosen value beside Final thoughts. Never put goals, ownership rationale, links, paths, or history in `finalThoughts`. Report only meaningful changes; do not relay duplicate monitor working/done notices or restate routine progress.
- Keep evidence summaries compact and link the complete artifact: state the outcome, the decisive evidence and any limit, and cite the artifact path or exact source that holds the full logs, screenshots, transcripts or file dumps instead of pasting them into task updates, delegation handoffs, progress notes or the final report. The summary never replaces required detail, so a reader opens the linked artifact when the detail matters.
- Verify implementation and fix outcomes end to end, not only statically. Proportionate real functional and runtime checks belong to completion, so when you are already authorized and equipped for it, run the supported user flow with its realistic inputs and state instead of handing it back.
- Treat safe, reversible local setup, service startup, and local configuration needed by the authorized outcome as part of the task. Inspect first, reuse owned healthy services, and start or change only the resource needed for this task. A specialized or project skill may set stricter startup rules; follow it. This does not authorize production or destructive changes, unexpected cost, provider or billing changes, new credentials or credential extraction, sensitive cross-account reads, or stopping or replacing services you do not own.

## Git authority

Local committing, pushing, merging, releasing, and deploying are separate decisions.

- **Automatic local milestone commits.** After an authorized implementation milestone is verified, discover the installed local commit skill from the available skills list (`commit` in Astack, or its documented equivalent) and invoke it with the owned paths, verification result, and check evidence instead of committing inline. If no such skill is available, follow this contract directly and report the fallback. A milestone is eligible only when the change set is coherent and workable, the checks and verification passed, and ownership is unambiguous. Coherent means one owned outcome rather than mixed user, agent, or task work. Workable means the change is complete enough to pass its proportionate checks and configured hooks.
- **Staged-entry stop condition.** Before an automatic commit, the index must be empty. If any pre-existing staged entry exists, skip the commit and leave the checkout as it is; do not reset, unstage, stash, or try to separate those entries. If any other changed file or hunk might belong to someone else, skip as well.
- **Preserve other work.** Stage only the owned paths with explicit paths. Do not use broad staging such as `git add -A`, `git add .`, or `git commit -a` when other work is present. Leave unrelated changes and pre-existing staged changes untouched, and report any files left out.
- **Checks and hooks.** Run the checks appropriate to the owned change set and let configured hooks run normally. Never pass `--no-verify` or use another hook bypass. If a check or hook fails, fix the owned change or stop and report the failure; do not commit a broken milestone.
- **Push.** Pushing requires a separate explicit user invocation and belongs to the user-invoke-only `push` skill. `implement` never invokes it automatically and never pushes inline. That skill checks applicable formatting, lint, and configured hooks and never force-pushes.
- **Merge and release.** Merging into a shared or default branch, version bumps, release tags, publishing, and deployment require separate explicit authorization. A local commit or push is never merge or release permission. Follow the repository's release workflow and the `release-status` skill; a local tag is only a local label. Read-only skills and any explicit no-commit instruction keep their own limits.

## Navigation and auth contracts

For changes that touch navigation or authentication, statically trace every affected link to the routes the application actually registers, not only the routes the change was written against. Check app-owned links and links rendered by an SDK or identity provider separately: the rendered origin, path, hash, query and redirect mode can differ from the app's own router. Cover the flows in both directions, such as sign-in to sign-up and back, and cover sign-out or account switch only where that session is already authorized. Check that any `next`, return, callback or post-auth destination is handled by the application's existing destination-validation boundary and permitted origins or paths instead of assuming a new allowlist. Keep this check proportional to a navigation or auth change; unrelated work does not need it.

Static tracing proves configuration, not that a click lands where intended; following the links is a separate runtime step. A route table, link inventory or passing build is static evidence only. When existing permissions already allow it, run the click-through yourself: for a browser app use Aside first through its skill or guide, start at the real entry route, follow the actual supported flow with the intended signed-in state, and confirm the destination origin and path. An implementation request does not by itself grant login, production or paid access. Mark the result **NOT RUN** only when a concrete input, access, tooling or permission is missing, and then give exact steps (starting route, control, expected origin and path) with that dependency. Never report an unexecuted check as a pass.

## Scope discipline

- Build only the current requested outcome and changes necessary to deliver it. State the smallest complete outcome and non-goals in the existing plan, not another document; keep `taskInfo` to hidden coordination metadata. Agent-written acceptance criteria cannot authorize extra requirements. Earlier authorization is not a standing instruction to resume unrelated unfinished work or paid verification; carry earlier work forward only when the current request continues it.
- Default to no additional runtime machinery. Estimators, reservation pools, repeated checksums, recovery systems and blocking gates require an explicit requirement or demonstrated failure that the approved task must address. Hypothetical robustness is not justification. Reuse platform and trusted-boundary guarantees; count false refusals, latency and recovery burden as costs. Omit optional or duplicate checks rather than implement them by default. Preserve essential authorization, untrusted-input validation and data-loss protection.
- Compose existing capabilities before creating infrastructure. New persistent state, recovery behavior, lifecycle ownership or public abstractions must be necessary for a concrete requirement or demonstrated failure within the approved scope. Generic robustness, production-readiness and hypothetical future cases do not expand that scope.
- Instructions governing how the agent coordinates work are not automatically requirements for runtime machinery in the code being built. Keep policy with its existing owner unless moving it is required by the task.
- If the smallest complete solution requires materially broader guarantees or scope, explain the tradeoff and obtain direction before expanding. Otherwise choose the smaller solution and proceed without unnecessary approval prompts.
- When the destructive boundary is genuinely ambiguous, clarify it before adding safeguards: for example, whether a target is an entire disposable test account or shared real data. Do not ask when the request already makes that boundary clear. Judge the actual risk once it is known, and drop speculative safeguards that risk does not require.
- Keep essential validation, security, cancellation handling and data-loss protection. Simplicity means removing unnecessary guarantees and machinery, not hiding errors or leaving required behavior incomplete. Stop when the requested behavior and allowed verification are complete; optional hardening is not a new task.

## Diagnose failures and recover

A failure, timeout, or retry limit is a diagnosis checkpoint, not an automatic reason to hand off unfinished work. Actively investigate the cause and pursue the authorized outcome while a safe, evidence-backed next step remains.

1. Inspect the actual error, available full logs, exit/stop reason, failed stage and relevant process/tool state. Preserve useful evidence. Distinguish application defects, tooling failures, missing prerequisites and unknown outcomes; do not invent a root cause.
2. Form a specific hypothesis and use the smallest safe diagnostic to test it. For a stalled build, identify the unfinished task and inspect or rerun that task alone with useful output rather than restarting the whole build blindly.
3. Apply the smallest supported correction or documented fallback, then retry the affected step and verify its result. Record what changed and why it addresses the evidence. A retry must test a concrete hypothesis or follow a verified correction; repeating an unchanged attempt is not recovery.
4. Keep attempts and waits bounded. Increase a timeout only with evidence of legitimate progress or a known expected duration, never merely to hide a stall. Do not manufacture monitor progress, spin indefinitely, or build recovery infrastructure for a one-off failure.
5. Preserve authorization, resource ownership and specialized fail-closed limits. Check the actual outcome before retrying any operation with possible side effects; never replay an uncertain write, submission, paid action or destructive operation. Do not bypass consent, credentials, helper boundaries or explicit refusals.
6. Continue diagnosis, safe recovery and independent authorized work without asking the user to approve already-authorized actions. Keep the task active while doing that work. Use blocked only when the next step waits for a user decision (a response, approval, or permission) or another agent's output or review, and supply `dependentOn` with exactly one of those two values; a previous failure, external service, tool failure, or other obstacle that fits neither category is not blocked status. Preserve safety, keep the task active, and report that unavailable dependency truthfully.
7. Before stopping with incomplete verification, establish the concrete blocker: evidence inspected, causes confirmed or still unknown, recovery attempts and their observed results, safe alternatives evaluated, and the exact dependency or condition needed to resume. Name who or what must supply the missing authority, access, service, configuration, or decision and which check can then run. A bare timeout, attempt count, or "needs setup" is not enough. Do not ask someone else to perform routine local setup, startup, restart, or verification you can safely complete within the authorized scope. Seek human input only for a genuine missing authority or an unclear scope/risk decision, including production or destructive changes, unexpected cost, sensitive data, new credentials or secret provisioning, or interference with a service you do not own. If no supported safe path remains, report that limit honestly; neither claim success nor promise guaranteed root-cause discovery. Report source-level completion separately from live execution that is blocked by unavailable access, and state that limit once instead of probing repeatedly for access.

## Files

Use repository-relative `var/`, never the system `/var/`. When you need your own artifact path, read the current session ID from the agent's own shell tool:

```bash
printf '%s\n' "$PI_SESSION_ID"
```

Use the full value as `sessionId`, not a Herdr pane ID, an invented agent name, or an inherited parent identity. Require a nonempty single directory component matching `[A-Za-z0-9][A-Za-z0-9_-]*`, and real tool-returned `W<number>` / `T<number>` IDs. If you are reading or writing your own artifacts and this identity is missing or unsafe, stop and report the blocker; do not guess, truncate, or silently sanitize it. A First Mate coordinator cannot run the shell lookup by design: that intentional restriction is not a missing identity record and must not block AgentCreate or delegation.

The root agent's task directory is:

```text
var/<sessionId>/<workId>/<taskId>/
```

A delegated agent uses the exact parent task directory supplied in its assignment as `parentTaskDir`, then appends its own session-local IDs:

```text
<parentTaskDir>/<childSessionId>/<childWorkId>/<childTaskId>/
```

Apply this recursively at every allowed delegation depth. Resolve paths against the target repository root and keep resolved destinations, including symlinks, inside that repository's `var/`. Record the canonical artifact directory and any parent session/Work/Task IDs in `taskInfo`; pass them unchanged in handoffs and return them with results. On resume, verify that the recorded directory belongs to the current assignment before reusing it. Session branches can restore different tracking records, so matching numeric IDs alone do not authorize overwriting existing artifacts.

pi-herdr AgentCreate does not need the shell session lookup or a pre-created directory. It derives the delegated task directory from the host session and real Work/Task IDs and creates it. In a root session omit `parentTaskDir`; in a delegated session pass the exact `parentTaskDir` from your assignment so the new directory stays nested. Do not pre-create it or read the session ID just for AgentCreate. A coordinator whose shell is intentionally restricted can still delegate: use AgentCreate's returned `taskDir`/`reportPath` as the canonical delegated path, and do not stop to request shell access. Direct Herdr Core CLI launches keep the manual path preparation described by the `herdr` skill.

Create directories only when artifacts are useful. Feature names belong in descriptions, not path selection. Switching tasks switches to that task's directory. Keep shared plans and DAGs in the coordinating task's directory and link them from other tasks rather than duplicating them. Preserve existing feature-named artifacts; do not move or reinterpret them without explicit migration approval. Specialized skills keep their safety and file-format contracts; if a helper requires an incompatible legacy path, report the incompatibility rather than inventing unsupported arguments or silently reverting to a feature-named directory.

Generated runtime defaults are not agent task artifacts. A tool with no real Work/Task context, such as a package persisting its own question or image state, writes under a documented package-owned namespace inside the repository `var/` (for example `var/<sessionId>/pi-decisions/`) and uses only the identity it actually has; never invent Work, Task or session IDs. This does not waive the agent's own required Work and Todo tracking, does not relocate intentional project configuration or skills, and does not override an explicit user or caller destination for a deliverable.

Use only the files that help, normally:

- `plan.md` — goal, constraints, affected areas, risks, and a short checklist;
- `dag.md` — Todo-linked task dependencies and assignments for substantial multi-area work only;
- `progress.md` — current status, delegated outcomes, and blockers;
- `summary.md` — changed files, static and runtime verification with their outcomes, review result, and any blocked check with its dependency.

Edit these files directly and keep their contents readable.

## Workflow

1. Establish real Work/Task IDs. Establish session identity and the canonical task artifact directory when you will read or write artifacts yourself; AgentCreate derives and creates a delegated task directory from host session context without shell, so a missing coordinator shell does not block delegation. Write a short plan and checklist when useful; a small task needs only a concise plan.
2. Read project instructions, matching flow documents, current behavior, and applicable decision files.
3. Identify the owning boundary, acceptance criteria, edge cases, compatibility concerns, and rollback risk. Before non-trivial interface changes, new abstractions, or responsibility restructuring, read the global `codebase-design` skill fully and record its scaled design contract in `plan.md`. Reuse approved design decisions rather than reopening them without new evidence; a straightforward local fix needs only a brief ownership/contract check.
4. Record each task's `self` or `delegate` decision and reason in hidden `taskInfo`; record the visible update in `finalThoughts`. For substantial multi-area work, map outcomes and dependencies in `dag.md` before assigning any coding agents; follow the DAG workflow below. For small or tightly coupled work, skip the DAG; the recorded ownership reason is sufficient.
5. Execute only the authorized assignment through its owning specialized skill, follow ready DAG nodes when one exists, and keep the checklist current. Change production files only when implementation is authorized.
6. Inspect the combined change for overlapping or conflicting edits.
7. Run only checks allowed by the user and the owning skill, once per necessary scope. For implementation, applicable non-unit checks include formatting, linting, type checking, builds, or schema validation. Those static checks stay necessary but are not substitutes for behavior. Before claiming the work complete or fixed, verify proportionately and for real: reproduce the reported defect where possible, then exercise the actual supported user flow with the real intended input and state and confirm the persisted or terminal outcome. When a supported check needs a local service or dependency, inspect and reuse an owned healthy instance, recover only the missing or stale resource you own, verify readiness, and rerun the check instead of handing back routine local startup or configuration. For a browser app use Aside first through its skill or guide, not a substitute surface presented as the original. Check meaningful UI timing and state too, such as a prompt clearing only after admission or surviving a failure and new edits, not just a final screenshot or optimistic bubble. Proportionately affected recovery paths are part of the same journey. An HTTP 200, accepted upload, build, lint result or source review only proves its own layer and never eventual operation or model success. Run unit tests only when the latest user request explicitly allows them. This does not order broad audits, extra agents, fixed test counts, or indefinite polling. It also does not authorize paid model or inference use, destructive or production actions, login or credential extraction, or sensitive cross-account reads; seek consent only where it is genuinely missing for one of those, not as redundant approval for safe checks the request already authorizes. When a concrete input, access, tooling or permission is missing, diagnose the supported safe recovery first; if none exists, mark the task blocked or the check **NOT RUN** with the exact evidence and dependency and report the outcome as source-only or incomplete rather than done. After later changes or new evidence, rerun only the checks those changes affect; do not repeat an empty verification or review cycle. For an eligible verified milestone, apply `Git authority` by discovering and invoking the local commit skill before reporting completion.
8. Before reporting, confirm that the runtime verification above ran against the changed behavior. Prepare exact manual steps only for a check you could not run yourself, and name the missing dependency instead of asking the user to retest a flow you were authorized and equipped to verify. When the change altered user-visible UI, also complete the narrow UI testing hand-off below.
9. Review directly for small or isolated changes. Group review and communication at coherent, stable milestones instead of after every intermediate step; report the outcome, decisive evidence, owner, and exact next action, and do not repeat unchanged waiting states. Add an independent `agent-review` only when the clarified risk, breadth, uncertainty, or an explicit request warrants it; neither independent review nor extra delegates are default steps. When a change affects authentication, authorization, secrets, data isolation or another security control, keep an independent security review with an owner separate from the implementer; milestone grouping does not replace it.
10. Write the final summary and report the outcome. After writing a synthesis artifact, immediately verify its exact canonical path with `test -f <path>` and, when it contains a case matrix, compare the recorded case IDs against the assigned case set before handoff. A write tool's success response alone does not prove the artifact landed where the parent expects it or that every case row is present; copy or correct it before reporting completion.

## Post-implementation UI testing

A task that changes user-visible UI gets one extra, narrow step after functional verification, and nothing more:

- Hand the changed surface to the `ui-ux-testing` skill in its authorized fix-or-flag mode, scoped to the UI this task changed. Record the phase and mode as the hand-off starts; that skill needs the declaration before it audits.
- Its read-only audit covers rendered contrast against the painted surface and, for shell or theme changes, explicit outer-frame edges and corners. Auto-fix is limited to clear, reproduced defects against the repository's existing design system, components and copy rules. Subjective changes, new patterns, new dependencies and copy-intent changes require the user's own decision, so they are never made silently.
- Do not hand off when the user opted out, asked for a read-only review, is not authorized to change that UI, or the change has no user-visible UI. A task without UI stays an ordinary implementation task, and a read-only, audit, research or planning request never becomes a repair.
- When the user names a UI surface to review without a prior implementation, use that skill's review mode with flag decisions: it starts read-only and changes nothing until the user selects an option or authorizes a repair.
- The skill rechecks every fix at runtime with an owner independent of the fix author and reports its findings; it never replaces this task's implementation or functional verification. If the skill or its runtime access is unavailable, report the skipped UI verification as an open limit instead of calling it passed.

## DAG and Todo workflow

For substantial multi-area work, the parent creates one Todo under the current Work for each concrete DAG node, including a final integration/verification node. Write `dag.md` in the working folder before dispatch. Use a small table with **Todo ID, outcome, dependency Todo IDs, owner, owned resources/write boundary, and status**; keep each Todo's hidden `taskInfo` to coordination metadata and put acceptance criteria in the assignment and plan, with concise `finalThoughts` for the visible status. Check that every dependency exists, the graph has no cycles, and parallel coding nodes have non-overlapping ownership. Use real IDs returned by the tracking tools; never invent Work or Todo IDs. If tracking tools are unavailable, do not dispatch delegated work.

A node is ready only when every dependency is **verified completed**. Assign ready, independent nodes to the parent or Herdr Pi agents; start dependent nodes only after their prerequisites are checked. Give each worker its node's outcome, context, owned and forbidden resources, acceptance criteria, allowed checks, and report format (changed files, checks, blockers). Do not mutate resources assigned to another worker concurrently. Keep shared interfaces and tightly coupled edits with one owner; use the global `herdr` skill for agent lifecycle, not a new script or worktree.

The parent owns the DAG and its session's Todos; workers do not update the parent's session records. Each worker creates or resumes its own session-local Work and Todos before assigned work, records the parent assignment in its details, and returns its local IDs with its results. IDs are session-scoped, so do not assume a parent's IDs identify records in a worker's session. Mark a node active in both places when work starts. Read the complete worker result and actual changed files before marking its Todo **and** DAG row completed; a worker's claim of completion alone does not unblock dependents. For partial or failed work, mark both blocked, mark dependent Todos blocked with their prerequisites and resume conditions, and update the plan or assignment before resuming. When dependencies or scope change, update `dag.md` and the affected Todo details together. Finish the integration node only after the parent reviews the combined diff and runs applicable checks. `progress.md` may record extra notes, but must not be a competing task list.

## Self or delegate

Evaluate each task before execution and whenever its scope changes. Record `owner: self` or `owner: delegate` and a brief evidence-based reason in hidden `taskInfo`; use existing fields, not a second tracking system. Use `finalThoughts` for the visible update only.

Delegate only when all of these hold:

- The bounded outcome, acceptance criteria, and allowed checks are clear.
- The resource and write boundary, or read-only investigation scope, can be isolated without concurrent conflicting edits.
- Required inputs and shared contracts are ready; prerequisites are verified.
- Useful parallel work or independent expertise outweighs startup, context transfer, monitoring, and integration costs.
- The owning skill permits delegation and required tracking and monitor tools are available. A missing coordinator shell is not a missing delegation prerequisite when AgentCreate is installed.

Otherwise keep the task with the current agent. Small straightforward changes, tightly coupled edits, shared-interface design, and work whose boundaries cost more to explain than to complete normally stay with one owner. Size or risk alone does not justify parallel coding; an independent review may still be appropriate. Do not use arbitrary file-count, worker-count, or delegation-depth thresholds. Every coding child applies the same decision rule when further delegation is allowed, while its parent retains responsibility for integration and verification.

## Delegation

Every delegated Core agent must have a continuous monitor before prompting. When the user or the active harness asks for app-presented workers, it also needs its own dedicated visible Task-ID-named Herdr app tab; otherwise the default Core-only terminal needs no Herdr app, space, tab or adoption label.
